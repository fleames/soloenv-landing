Features

Built to share work, not to run a platform.

Ship a link, not a deploy

soloenv up detects your compose.yaml or Dockerfile, builds it, runs it, and exposes it. One command, no config files.

Use case Send a client today's build before standup — without a deploy pipeline.

Your whole stack, not one port

Runs your real compose project — web + database + workers — exactly as defined. No framework lock-in, no rewrites.

Use case QA the full app against its real Postgres and Redis, just like production.

Locked by default

--protect puts HTTP basic auth in front of your app via a built-in reverse proxy. The tunnel only ever sees the protected entrance.

Use case Share a work-in-progress without it getting indexed, scraped, or leaked.

Expires so you don't have to remember

--ttl 4h tears the whole environment down on a timer — containers, proxy, and tunnel all stop together.

Use case A demo link that dies after the call. No zombie tunnels running overnight.

Close the laptop, keep the link

--detach runs everything in the background and survives your terminal closing. soloenv down stops it cleanly.

Use case Leave staging up on a cheap VPS for the weekend while testers poke at it.

A preview URL on every PR beta

A drop-in GitHub Action comments a live preview URL on each pull request, so reviewers click instead of pulling the branch.

Use case Reviewers test the running app from the PR — no local checkout required.

Honest answers

"Why not just use…?"

Fair question. Here's where each alternative stops and SoloEnv starts.

Why not ngrok?

ngrok tunnels a single port you're already running. SoloEnv builds and runs your whole Docker stack first, then tunnels it, adds basic auth and a TTL, and tears it all down on down. ngrok is a pipe; SoloEnv is the environment behind it.

Why not Cloudflare Tunnel?

SoloEnv uses Cloudflare quick tunnels under the hood — you just skip the named-tunnel setup, DNS records, config files, and credentials. One command instead of a cloudflared config project, plus Docker orchestration, passwords, and auto-expiry on top.

Why not Railway / Render?

Great hosted platforms — but they mean another account, billing, build configuration, and pushing your code to their cloud. SoloEnv runs the exact image on hardware you control and shares it. No vendor build step, no migration, $0 to start.

Why not Vercel previews?

Vercel previews are excellent for frontends and serverless deployed on Vercel. SoloEnv is for full Docker backends — Django + Postgres, Rails + Sidekiq, anything with a database — running anywhere. Different stack, different tool.

Why not just use production?

Because the first time a broken migration or a half-finished feature meets real users shouldn't be in prod. SoloEnv gives you a throwaway, password-protected URL to test the real stack before it ships.

Built in the open

No black box. Read the code, run the binary.

SoloEnv is a single open-source Go binary. It orchestrates Docker and Cloudflare on your own hardware — there is no SoloEnv server in the request path and nothing to sign up for.

.github/workflows/preview.yml 
# Comment a live preview URL on every pull request
name: preview
on: [pull_request]

jobs:
  preview:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: fleames/soloenv-action@v1
        with:
          ttl: 2h
          protect: true

Real GitHub Action (beta) — drops a preview link straight into the PR.

  • Your code stays local. Containers run on your machine or VPS; only HTTP traffic is proxied through Cloudflare's edge.
  • HTTPS out of the box. Every URL is a valid-cert https://…trycloudflare.com address.
  • Auditable. MIT-licensed, ~single binary. Read every line on GitHub.
  • Prebuilt for every OS. macOS, Linux, and Windows binaries on each release.

Straight talk: what SoloEnv is not

  • Not production hosting. It's for staging, demos, and reviews — not running your SaaS.
  • Not a permanent URL (yet). Free quick-tunnel URLs rotate on restart; stable URLs are coming with the hosted version.
  • Not a webhook debugger. Need request inspection and replay? ngrok is genuinely better at that.
  • Not zero-latency. Traffic routes through Cloudflare's edge — great for sharing, not a CDN.

FAQ

Developer questions, answered straight.

Is my code uploaded to your servers?

No. Everything runs in Docker on your own machine or VPS. SoloEnv only opens a Cloudflare tunnel to proxy HTTP traffic to your local app — there is no SoloEnv server in the request path, and your source never leaves your box.

How does the password protection work?

--protect starts a small built-in reverse proxy with HTTP basic auth in front of your app and tunnels that. Visitors hit the auth wall before they ever reach your running stack. SoloEnv generates a username/password (or you can supply your own).

Is the connection encrypted? Do I get SSL?

Yes. Cloudflare quick tunnels are HTTPS end-to-end, so you get a https://…trycloudflare.com URL with a valid certificate automatically. No cert wrangling.

What about performance and latency?

Traffic hops through Cloudflare's edge network, so expect normal tunnel latency (typically tens of milliseconds). That's ideal for demos, QA, and code review. It's a sharing tool for staging, not a production CDN.

Does it work with Docker Compose?

Yes. SoloEnv auto-detects compose.yaml / docker-compose.yml and runs the whole multi-service stack, or builds and runs a single Dockerfile. No changes to your existing files.

What do I need installed?

Docker and the soloenv binary (a single Go executable). cloudflared is fetched automatically the first time. No cloud account, no API keys to start.

Can I use it in CI/CD?

Yes. The CLI runs headless with --detach, and there's a GitHub Action (beta) that posts a preview URL on each pull request. Pin a release version in CI for reproducible runs.

Can my whole team use the same URL?

Yes — share the URL and password. Anyone with the link reaches your running stack until it expires or you run soloenv down. Great for client reviews and remote QA.

How long can an environment stay up?

As long as the process runs. Use --ttl to auto-expire (e.g. --ttl 168h for a week) or leave it running with --detach and stop it with soloenv down when you're done.

Is the URL guessable? How private is it?

Quick-tunnel URLs are random *.trycloudflare.com subdomains. Combined with --protect, they're suitable for private sharing. They are not meant for permanent public hosting.

Can I use my own custom domain?

Not with free quick tunnels. Custom domains via named Cloudflare tunnels are on the roadmap — and a headline feature of the upcoming hosted version. Join the waitlist to get it first.

Which operating systems are supported?

macOS, Linux, and Windows — prebuilt amd64 and arm64 binaries ship with every release. Docker is the only hard dependency.

Is this production-ready hosting?

No — and that's by design. SoloEnv is for staging, previews, and demos: "share the real app safely," not "run my SaaS on it." Use it to validate before you ship to your real infrastructure.

What does it cost?

The CLI is free and open source under the MIT license. Quick tunnels run on Cloudflare's free tier with no account required. The hosted version (in progress) will add paid convenience features — the CLI stays free.

How do I stop everything and clean up?

soloenv down stops the tunnel, the auth proxy, and your containers, then clears local state. With --ttl it happens automatically — no leftover processes.
